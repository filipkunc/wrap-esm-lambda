# v0.2.0 — the exports tap is the whole toolkit

The release where the project outgrew its name. `wrap-esm-lambda` began as a
native transform that wrapped one AWS Lambda handler; it is now a general,
declarative instrumentation toolkit built on one mechanism — the **generic
exports tap** — and this release removes the original transform entirely.
You describe what to patch (package name + semver + files, or plain paths)
and write an imperative patch function; the tap hands it the module's live
bindings, for `import` and `require()` alike, at runtime or at build time
from one config.

## Highlights

- **Tap-only surface.** Wrap entries (`match` + `handler` + `wrapper`) are
  gone from the config, the engines and the native addon. A wrap entry
  translates to a patch entry in three lines; the engine contract moved to
  version 2 so mismatched core/engine pairings refuse loudly.
- **The Lambda story, generalized.** `module: { path: [...] }` matches code
  with no package identity, and `@wrap-esm-lambda/hooks/aws-lambda` derives
  the handler entry from `_HANDLER`/`LAMBDA_TASK_ROOT` at preload — the
  same contract AWS's runtime interface client reads, reproduced rule for
  rule. Nothing about the handler is written down; outside Lambda the same
  config is inert. Verified against the real RIC on the real
  `public.ecr.aws/lambda/nodejs` images, both module systems.
- **Lazy engine binding.** Importing core costs no engine; the native oxc
  addon (or the pure-JS acorn engine) binds on first use, and an inert
  config never loads one — while a real config still binds at startup, so
  engine failures stay loud. This cut the runtime shell's cold start from
  ~74 ms to ~58 ms and its peak RSS by ~4 MB on the reference fixture.
- **Fail-soft failure policy.** Every failure downstream of a valid config
  costs exactly what it must: a broken patch drops one entry, a drifted
  binding skips one module, and everything is reported once and retrievable
  via `instrumentationFailures()`. `wrap-esm-lambda-validate` turns config
  drift into a CI failure ahead of time.

## Breaking changes

- `WrapperSpec`, `WrapEntry`, `transformMatched` and the addon's
  `transformLambda*` exports no longer exist; `InstrumentEntry` is an alias
  of `PatchEntry`.
- `TAP_CONTRACT_VERSION` is 2; `selectEngine` is synchronous and
  `engineName` is a function.
- Migration for a wrap entry: `module: { path: ['<handler file>'] }`,
  `bindings: ['<handler>']`, and a patch function
  `bindings.handler = WrapAwsLambda(bindings.handler)` — or, on Lambda,
  just `lambdaHandlerEntries()`.
