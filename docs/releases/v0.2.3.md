# v0.2.3 — the cold-start numbers, corrected

No changes to the published packages. This release corrects v0.2.2's
cold-start comparison, which measured the wrong thing and said so
confidently — this page supersedes that one's "the difference is what
runtime delivery costs" claim.

## What was wrong

v0.2.2 compared the runtime hook on the unbundled app against the
unplugin-built bundle and attributed the whole gap to runtime delivery.
Two deployments, one number, three flaws:

- **The deliveries are not substitutes.** Bundling erases the module
  boundaries the runtime hook's package entries match — inside a bundle,
  hono and `@smithy/core` never load as modules, so only the handler's own
  path entry survives; and an unbundled deployment gives the unplugin no
  build to ride. The comparison implied a choice that exists on neither
  artifact.
- **About half the gap was the bundling win itself** — one file versus
  cold-importing hono and the AWS SDK from `node_modules` — a packaging
  fact, not an instrumentation cost.
- **Sequential measurement flattered whoever ran second**: later legs
  inherited a warmer page cache, which made the two engines look tied
  when their fixed costs differ (the native binding loads in 0.7 ms and
  transforms hono's defining module in 0.2 ms; the acorn engine spends
  37 ms importing its own parser and 8 ms on the same transform).

## The corrected measurement

Each delivery priced against its own uninstrumented control on the same
artifact, five real-emulator boots per leg, **interleaved round-robin**
(hyperfine's discipline), medians —
[`examples/hono-lambda/coldStartTable.md`](../../examples/hono-lambda/coldStartTable.md):

| leg                                          | billed cold start | RSS   |
| -------------------------------------------- | ----------------- | ----- |
| unbundled — no instrumentation               | 248 ms            | 82 MB |
| unbundled — runtime hook, oxc engine         | 288 ms (+40)      | 94 MB |
| unbundled — runtime hook, acorn engine       | 308 ms (+60)      | 91 MB |
| unbundled — orchestrion (smithy Client#send) | 344 ms (+96)      | 99 MB |
| bundled — no patches                         | 182 ms            | 68 MB |
| bundled — patches baked (unplugin + esbuild) | 183 ms (+1 ≈ 0)   | 68 MB |

**The runtime hook costs +40 ms at cold start with the native oxc engine
and +60 ms with the pure-JS acorn engine; orchestrion instrumenting the
same `@smithy/core` `Client#send` costs +96 ms; patches baked at build
time cost nothing measurable.** Bundling's own ~66 ms saving belongs to
the packaging choice, whichever delivery is used.

## What enforces it now

- The CI Lambda lane measures both within-artifact contrasts live on
  every push — five containers, with the uninstrumented controls asserted
  **silent** so the contrast cannot quietly void itself — and prints both
  deltas on the job summary and the sticky per-PR comment. Live runs
  across this release's pull request landed hook cost +27…+35 ms and
  unplugin cost +2…+13 ms, consistent with the committed reference.
- Engine selection is documented where unplugin users look
  ([`@wrap-esm-lambda/unplugin`](../../packages/unplugin/README.md#which-engine-transforms-your-build)):
  oxc by default, `WRAP_ESM_LAMBDA_ENGINE` to select, acorn fallback on a
  missing addon — and for build-time delivery the engine ships nothing,
  so the bundle's runtime numbers are engine-independent. The cold-start
  table records which engine built its bundles, because provenance should
  not have to be inferred.

## Compatibility

Package surfaces, the engine contract and the config format are unchanged
from 0.2.2.
